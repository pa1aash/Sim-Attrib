**Session G4, 2026-08-20.** The first adversarial pass this project has ever run, and the first
run against **its own** output rather than against a paper it wanted to cite. Four sessions of
verdicts, every one single-pass, and the two things that have changed this project's direction
both arrived by accident.

Written to the standing instruction carried from G0 onward: **the strongest case against comes
first.** Here that means the case against `results/jacobian_rank.S_A.yaml` and
`results/jacobian_rank.S_B.yaml` — the only favourable empirical result this project has.

Every number quoted below is reproduced from `results/robustness/ROBUSTNESS_TABLE.md`, which is
generated by `src/diagnostics/report_robustness.py` from the YAML files. No number in this
document was typed by hand (S11).

# VERDICT: **THE TWO SUMMARY SETS COME APART. `S_B` STANDS WITH A SMALLER MARGIN; `S_A`'s RESULT DOES NOT GENERALISE.**

G3 reported one verdict — *"two of the three summary sets separate the components"* — and this
session finds that the two are not equivalent and should never have been quoted as a pair.

- **`S_B` (ten binned counts) — STANDS.** It separates under both the base family set and an
  adversarially constructed one. Its margin is materially smaller than the base result suggests
  and its separation cost rises about forty-fold, but the verdict holds.
- **`S_A` (four epidemic-curve features) — the *generalisation* is OVERTURNED.** The number in
  `results/jacobian_rank.S_A.yaml` is correct and reproducible; what fails is any reading of it
  as a statement about the simulator. Under a first-attempt alternative triple of distortion
  families, `S_A`'s condition number rises 25-fold past the pre-registered ceiling and the
  verdict flips to INSEPARABLE.

**Nothing here says a singular value is wrong.** Everything G3 computed is correct, reproducible
from the recorded seed and commit, and was computed with the pre-registered thresholds
unrevised. What moves is **what the numbers license**, and in one place a documented claim about
the code is simply false.

This session was commissioned on the premise that a favourable self-produced result gets the
same scrutiny as everything else. The qualifications below are therefore stated at their real
size, including the two that are favourable to the project (`S_B`'s survival, and `S_A`'s
reported numbers turning out uncontaminated) — S10 cuts both ways and a critic pass that only
reported bad news would be as unreliable as one that reported none.

## 1. The gapless-spectrum objection

**Verdict against G3's claim: STANDS at `K = 3` — the objection does not describe these spectra.
But it is DEFERRED rather than defeated, and what defers it is a design choice, not the model.**

`audit/R2_THREAT_CHECK.md` §1.3 records the objection: Gutenkunst et al. (2007) find
sensitivity spectra for models of this class *"spread roughly uniformly over many decades, with
no gap"*, and if there is no gap then "numerical rank at tolerance `τ`" reports where the
analyst put `τ` rather than a property of the model. `docs/DECISIONS.md` D-6 calls this *"a
second, sharper threat"* than the novelty question, and `GATES.md` G3 lists it under what the
gate does not certify. Nobody had measured it.

### 1.1 The objection as literally stated does not describe these spectra

Section 1 of `results/robustness/ROBUSTNESS_TABLE.md` is the like-for-like measurement. Both
spectra span **about one decade or less**, not many, and the decay is not uniform: in both sets
the largest adjacent ratio falls immediately after `σ₁`, and `σ₂` and `σ₃` sit close together
below it. Gutenkunst et al.'s picture — a smooth geometric slide across decades with nothing to
separate signal from noise — is not what a `d × 3` Jacobian of this simulator produces.

**No singular value is anywhere near `τ`.** The smallest is `σ₃/σ₁ = 0.186` for `S_A` and
`0.0988` for `S_B`, against `τ = 0.01`. The tolerance is not sitting inside a dense continuum
of singular values where a small nudge would move the rank; it sits an order of magnitude below
everything. So the specific failure mode the objection describes — an arbitrary cut through a
gapless spectrum — **did not occur here**, and `docs/THRESHOLDS.md` §1.4's unresolved-value
rule, which was the pre-registered place it would have surfaced, correctly did not fire.

### 1.2 But the margin is one order of magnitude, and `S_B` flips inside it

The right question is not "is there a gap" but "how far can the tolerance move before the
verdict does", and that has an exact answer rather than a sampled one. The decision rule is
`σ_K ≥ τ·σ₁`, so the verdict flips precisely at

    τ*  =  σ_K / σ₁  =  1/κ .

For `S_A`, `τ* = 0.186`, which is **18.6×** the pre-registered `τ`. For `S_B`, `τ* = 0.0988` —
**9.88×**. Halving or doubling `τ` changes nothing for either set. **At one order of magnitude,
`S_B` flips to INSEPARABLE and `S_A` does not.** The brief asked for "half, double, and one
order of magnitude looser"; one of those three moves changes the answer for one of the two
sets, and the table in §1.2 of the generated file shows exactly where.

**One direction of "looser" is the tightening direction, and this is worth stating because it
is easy to get backwards.** `docs/THRESHOLDS.md` §1.2 derives `τ = 1/κ_max`, so raising `τ`
*tightens* the requirement (it is equivalent to lowering `κ_max` from 100 to 10) and lowering
`τ` loosens it. Every row of the sensitivity table moves the pair together, because moving one
alone would test a threshold pair the project never registered.

### 1.3 `S_B` sits 1.2% outside the project's own "comfortable" boundary

This is the sharpest form of §1.2 and it does not require anyone to disagree with the
pre-registered threshold at all. `docs/THRESHOLDS.md` §1.2 derives `τ` from a compute budget
via a table of its own:

| `κ` | replicates `n ≈ κ²` needed to separate components | verdict |
|---|---|---|
| 10 | ~10² | comfortable |
| 100 | ~10⁴ | affordable but expensive |
| 1000 | ~10⁶ | **not affordable** |

`S_B`'s measured `κ = 10.12`. The project drew its line at the third row — the point where
separation costs more than the whole study — and `S_B` passes that line with a factor of ten to
spare. But a reader who drew the line at the **first** row of the project's own table, the one
it labels *comfortable*, would call `S_B` inseparable **by 1.2%**. `S_A`, at `κ = 5.38`, is
comfortably inside on either reading.

That is not an argument for revising `τ`, which `docs/DECISIONS.md` D-6 and `LEDGER_DESIGN.md`
D3 both forbid after the fact and which this session does not do. It is an argument about how
the number may be *described*: **`S_B` is separable at the registered threshold and is not
comfortably separable**, and a paper that reports "both sets are separable" without that
distinction is reporting a threshold decision as though it were a structural finding — which is
the substance of the Gutenkunst objection even though the mechanism the objection names is
absent.

### 1.4 The two pre-registered criteria are one criterion, and the second can never fire

`docs/THRESHOLDS.md` §1.3 states that a set is inseparable if `rank(J) < 3` at `τ = 10⁻²` **or**
`κ > 100`, and adds — correctly, and to its credit — *"These are the same criterion stated two
ways for `K = 3`."* The arithmetic: with `d ≥ K = 3` and all singular values resolved, `rank = 3
⟺ σ₃ ≥ τσ₁ ⟺ σ₁/σ₃ ≤ 1/τ = 100 ⟺ κ ≤ κ_max`. Not approximately — identically, including at
the boundary, because `κ_max` was *defined* as `1/τ`.

The disclosure is in `THRESHOLDS.md` and it does not propagate. `results/jacobian_rank.*.yaml`
records `full_column_rank` and `condition_number` against `kappa_max` as two fields;
`results/SUMMARY_TABLE.md` prints them as two columns; the verdict string reads *"separable:
full column rank at tau **and** condition number within ceiling"*, and `audit/S3_REPORT.md`
§3.2 reproduces all of it. A reader who has not gone back to `THRESHOLDS.md` §1.3 sees a
conjunction of two independent checks passing, when what passed was one check reported twice.

In `src/diagnostics/jacobian_rank.py` the consequence is visible as unreachable code: the
`inseparable_reason` branch that reads *"condition number … exceeds kappa_max"* cannot be
produced at the pre-registered pair, because any spectrum that would trigger it has already
failed the rank clause. (It is reachable if a caller passes a `τ` and `κ_max` that are not
reciprocal, which the function permits, so it is not dead code in general — only at the
pre-registered settings, which is where every reported number comes from.)

This is the defect class `DEVIATIONS.md` **D-8** exists to name, applied to the verdict itself:
**under what condition would "condition number within ceiling" read FALSE while "full column
rank" read TRUE? There is none.** The design is disclosed and the reporting is not, so the fix
is to the reporting, not to the threshold.

### 1.5 What the objection survives on: `K = 3` is a choice, not a measurement

Section 1.1 is a weaker defence than it first appears, and the reason is the one Gutenkunst et
al.'s setting makes obvious. **Their models have dozens of parameters. This Jacobian has three
columns because the project declared three components.** A three-column matrix cannot display a
decades-wide gapless decay however badly conditioned the underlying model is; the narrow
spectrum may be a fact about `K`, not about the simulator.

`results/robustness/wide_spectrum_check.yaml` tests that directly, at no modelling cost: the
base and adversarial family sets are both exactly the identity at `η = 0`, are normalised by
the same prior-predictive standard deviations, and share the same `η_scale`, so their columns
live in one space and can be placed side by side to give a `d × 6` Jacobian over six distortion
directions of the same simulator. The test is deliberately set up so that the informative
outcome is the one against the project.

**And it is what happens.** `results/robustness/wide_spectrum_check.yaml`. For `S_B`, whose
`d = 10` leaves room for six columns without structural zeros, the six-column spectrum spans
**2.80 decades** against **1.01** for the three-column base — and the decay has no dominant
break: the adjacent ratios are `5.93, 2.46, 1.77, 4.23, 5.77`, none of them a gap. `τ = 0.01`
now falls *inside* the spectrum rather than an order of magnitude below it, between
`σ₄/σ₁ = 0.0388` and `σ₅/σ₁ = 0.00917`, and the rank at `τ` is 4 of 6.

**The tolerance-sensitivity changes by two orders of magnitude.** At `K = 3`, `S_B`'s verdict
survives `τ` moving by a factor of 9.88. At `K = 6`, on the same simulator with the same
summaries, **a 9.01% change in `τ` changes the rank from 4 to 5.**

| | `S_B`, `K = 3` (as reported) | `S_B`, `K = 6` |
|---|---|---|
| spread of the positive spectrum | 1.01 decades | 2.80 decades |
| largest adjacent ratio | 5.34 | 5.93 (and no break at all) |
| where `τ = 0.01` sits | an order of magnitude below `σ₃` | between `σ₄` and `σ₅` |
| change in `τ` needed to move the rank | ×9.88 | **×1.09** |

**So the objection is deferred, not defeated, and the thing deferring it is `K = 3`.** The
reported verdict's insensitivity to `τ` is a consequence of the component list being short. It
does not license the inference that rank is a well-behaved quantity for this simulator, and a
paper that presented `κ = 5.38` as though it were a natural break would be making exactly the
claim Gutenkunst et al. deny. `S_A` cannot even be tested this way — `d = 4 < 6` forces two
structural zeros — which is itself a reminder that `d` and `K` are both design choices standing
between the reader and any statement about the model.

## 2. The adversarial distortion family set

**Verdict against G3's claim: `S_A` OVERTURNED, `S_B` STANDS — and this is the finding that
matters most.**

`audit/S3_REPORT.md` §4.4 raised this itself, as **Q-12**, and stated it correctly: *"the
verdict is a statement about three specific distortion families"*, and *"perturbing the
reporting delay instead would make the observation column a timing distortion too … and could
plausibly give a different verdict."* It called the caveat real and left its size unmeasured.
The brief asked for the size to be measured, by deliberate construction rather than by search:
*"If constructing an adversarial family that fails was EASY, that is a significant finding …
and must be stated as such, not minimised."*

### 2.1 What was built, and why each family was chosen

The base triple is deliberately of three qualitatively different kinds — a prevalence
nonlinearity, a timing drift, and a pure amplitude error — and `src/simulators/sir3.py` says so:
*"so that the Jacobian's columns are not similar by construction."* **The adversarial triple is
deliberately of one kind.** Every family perturbs the same dominant feature of an epidemic
curve: its observed exponential growth rate. Each was specified against a named target
component, with the reasoning written into the module docstring, before the set was run.

| | family | target | why it should be hard to separate |
|---|---|---|---|
| `η₁′` TRANSMISSION | `β → β·exp(η₁)` | PROGRESSION | In `dI/dt = (βS/N − γ)I`, `β` and `γ` enter one scalar. A constant multiplier on either moves the net growth rate, and while `S/N ≈ 1` — the entire growth phase — the two are near-indistinguishable. They separate only through susceptible depletion. |
| `η₂′` PROGRESSION | `γ → γ·exp(−η₂)` | TRANSMISSION | The same aliasing from the other side. The sign is deliberate: `−η₂` makes `η₁` and `η₂` move `R₀ = β/γ` in the **same** direction, so the columns point the same way rather than opposite ways. |
| `η₃′` OBSERVATION | `ρ → ρ·exp(η₃·(t/T − ½))` | both, via the growth rate | Multiplying the reported series by `exp(η₃ t/T)` adds exactly `η₃/T_days` to its fitted exponential growth rate — the same summary coordinate `β` and `γ` move. |

**The transmission and progression choices are aimed at a defence this project wrote down and
then removed.** `sir3.py` explains that the base progression family is mean-centred *"so that to
first order `η₂` is not a constant rescaling of `γ`"*, because *"an uncentred version would alias
progression onto a pure rate change and would make the diagnostic's answer a consequence of the
parameterisation rather than of the model."* The adversarial set is that uncentred version, on
both rate constants at once. The project identified the aliasing and designed around it; the
attack is to stop designing around it.

**The observation choice is strictly harder than the one Q-12 named.** Q-12 proposes perturbing
the reporting *delay*. A delay **shifts** the reported curve; a reporting trend **tilts** it,
and tilt is what the other two columns do. A trend in ascertainment is also a real and common
epidemiological misspecification — surveillance improving over an epidemic — not a contrivance,
which matters, because an adversarial family nobody would write down proves nothing about
whether the diagnostic is fragile in practice.

### 2.2 The result — the two summary sets come apart

**`S_A` fails. `S_B` survives.** Both halves matter and neither should be reported without the
other.

| | `S_A` (`d = 4`) | `S_B` (`d = 10`) |
|---|---|---|
| base families | `κ = 5.378`, rank 3, **separable** | `κ = 10.12`, rank 3, **separable** |
| adversarial families | `κ = 136.7`, rank 2, **INSEPARABLE** | `κ = 64.62`, rank 3, **separable** |
| `κ` multiplied by | **25.4×** | **6.4×** |
| `σ₃/σ₁` under the adversarial set | `0.00732` — **below `τ = 0.01`** | `0.01547` — above `τ`, by 1.55× |

Four things follow, in descending order of how uncomfortable they are.

**(a) The set a domain modeller would actually choose does not survive.** `S_A` is described in
`docs/THRESHOLDS.md` §1.1 as *"the set a domain modeller would actually choose"*. Under an
alternative triple of families built from the same simulator, its third singular value drops
below the pre-registered tolerance and the verdict flips. **The favourable `S_A` result is a
property of the base family triple, not of the simulator.**

The confounded pair is named, and it is not the one the design primarily aimed at. The
adversarial `S_A` near-null direction is `v = (0.2312, −0.5272, −0.8177)` over
`(transmission, progression, observation)`, so the equivalence class is
**progression–observation** — the reporting *trend* is what cannot be told apart from the
progression rate change, while the transmission/progression aliasing the first two families
targeted shows up as high coherence (`μ = 0.958`) without being the null direction. The attack
worked through its third family rather than its first two.

**(b) The set the composition spec actually names does survive, and that is a real result.**
`audit/MMC_COMPOSITION_SPEC.md` §5 nominates `S_B` — *"the natural choice: it is separable, it
is what an SBI practitioner would use, and its coordinates are cheap"* — and `S_B` is separable
under **both** family sets. Ten binned coordinates buy robustness that four curve features do
not. Stated plainly because S10 cuts both ways: **this is a favourable finding and it was
produced by a check designed to be unfavourable.**

**(c) One sentence in the composition spec is now false and should be corrected before it is
used.** §5 says `S_A` *"is separable with a smaller condition number and is the better-
conditioned option"*. Under the base families that is true. Under the adversarial families the
ordering **reverses**: `S_A` at `κ = 136.7` is inseparable while `S_B` at `κ = 64.62` is not.
"Better-conditioned" is a statement about one family set and was written as though it were a
property of the summary set.

**(d) `S_B`'s surviving margin is small, and it is the number the next session needs.** `S_B`
passes at `σ₃/σ₁ = 0.01547` against `τ = 0.01` — a margin of **1.55×**, where the base run's
margin was 9.88×. In the currency `docs/THRESHOLDS.md` §1.2 uses, `κ = 64.62` means separation
costs roughly `κ² ≈ 4.2 × 10³` replicates rather than the `≈ 10²` implied by the base run's
`κ = 10.12`. **That is a forty-fold increase in the price of separation, and it lands directly
on the cost gate `audit/MMC_COMPOSITION_SPEC.md` §4 pre-registers.** Whatever `p_sel` turns out
to be, the multiplier it is multiplied against is not the one the base result suggested.

**The control behaved.** `S_C` failed under both family sets with an *exact* null direction,
as designed — under the base set its equivalence class is `{progression}`, under the
adversarial set `{progression, observation}`. A control that had started passing would have
invalidated everything else here.


### 2.3 How hard it was to build

**It was not hard.** One set was specified and one set was run. **No second candidate was tried
and none was discarded** — there was no search over families, and there is no file of rejected
attempts, because there were none. The reasoning in the table above was written into
`src/simulators/sir3.py` before the run and is in the commit that precedes the results file.

That is the answer to the brief's question, and it is the unfavourable one. The brief specified
in advance what each outcome would mean:

> *"If constructing an adversarial family that fails was EASY, that is a significant finding
> about how much the original 'pass' result depended on the specific choice of families, and
> must be stated as such, not minimised."*

So, stated without minimisation: **`S_A`'s separability is a property of the distortion
families chosen, and a first-attempt alternative built from standard-textbook misspecifications
of the same simulator destroys it.**

**And stated with the same absence of minimisation in the other direction, because S10 requires
it:** the brief's "EASY" branch was written for an outcome in which the adversarial set breaks
*the* result. It broke **one of the two summary sets and not the other**, and the one it did not
break is the one the composition specification already nominates. **An easily-built family set
that fails `S_A` is not the same finding as an easily-built family set that fails everything**,
and reporting it as the latter would be manufacturing a proportionate-sounding criticism of the
kind S10 also forbids. `S_B`'s survival is evidence, and it is evidence for the project.

### 2.4 What this does not mean

Three things it would be equally dishonest to conclude.

**It does not mean the base result is wrong.** The base run is correct, reproducible, and
correctly computed; findings 1 and 4 test that separately. Both verdicts are true statements
about their own family sets. Nothing here says the base numbers should be withdrawn.

**It does not mean the adversarial set is the "right" one.** It was built to fail. A set built
to fail failing is weak evidence on its own — which is exactly why the design is documented
per-family with a stated target, so a reader can judge whether the families are ones a modeller
would plausibly write down, rather than taking "adversarial" on trust. The claim being made is
about the **size of Q-12's caveat**, not about which triple is correct.

**It does not mean "the diagnostic doesn't work".** The diagnostic did what it is for: it
distinguished a family set whose components separate from one whose components do not, using
thresholds fixed in advance, and it named the confounded pair. **A diagnostic that returned
"separable" for both sets would be the alarming result.** The finding is about what may be
claimed from a favourable verdict, not about the instrument that produced it.

### 2.5 The consequence for how the result may be written

`audit/MMC_COMPOSITION_SPEC.md` §5 already carries the caveat in prose — *"Separability was
established for this simulator, these three distortion families, and this closed list of summary
sets"* — and now has a number attached to it. Two consequences follow, and neither requires
revisiting any threshold:

1. **No sentence of the form "this simulator's components are identifiable from these
   summaries" is available, and no sentence quoting `S_A` and `S_B` together is available
   either.** The available sentence names the summary set and the family set at once: *"under
   ten binned incidence counts, the components separate under both the base distortion families
   and an adversarially chosen alternative triple; under four epidemic-curve features they
   separate under the base families only."*
2. **Q-12 is answered on the merits and should be closed as answered rather than left as a
   scope call.** It asked whether a second observation distortion is in scope. The answer this
   session produces is that the *family set as a whole*, not the observation family alone, is
   what the verdict is conditional on — and that the conditioning is load-bearing rather than
   decorative.

## 3. The count-observation CRN finding — derived independently, then measured

**Verdict against G3's claim: STANDS as a degeneracy, WEAKENED as a finding, and one clause of
it is wrong.**

`audit/S3_REPORT.md` §4.1, and the `why_not_a_count_noise_model` field of every results file,
assert three things: that a count-valued observation layer under common random numbers makes
the simulator a step function of `η`; that the difference quotient is therefore *"either
exactly 0 or O(1/h)"* and *"no derivative exists at any h"*; and that *"shrinking h makes the
first case more likely, so the estimator converges confidently to zero"*.

The brief asks whether this is a genuine degeneracy or a numerical artefact of the specific
random-number scheme, because *"a genuine degeneracy is a real and citable finding about CRN
with discrete observation models; a numerical artifact means the code has a bug."* It is
neither exactly. It is a genuine degeneracy, it is textbook, and the third clause misdescribes
the failure in a way that matters.

### 3.1 The derivation

Fix a seed `ω`. Under common random numbers the simulator is a deterministic map

    η  ↦  y(η; ω) ∈ ℝ^T ,

and the estimator averages the central difference

    D_h(ω)  =  [ s(y(η+h; ω)) − s(y(η−h; ω)) ] / (2h)

over `R` independent draws of `ω`. Two separate questions hide inside "no derivative exists":

**(a) Does the pathwise derivative `∂_η y(η; ω)` exist?**

*Continuous multiplicative layer* — what the diagnostic actually uses:

    y_t(η; ω)  =  μ_t(η) · exp(σ z_t − σ²/2),      z frozen by the seed.

This is as smooth in `η` as `μ` is, with `∂_η y_t = (∂_η μ_t)·exp(σ z_t − σ²/2)`. The pathwise
derivative exists, and under dominated convergence `E[∂_η y] = ∂_η E[y]`, so infinitesimal
perturbation analysis is valid: `D_h` has `O(h²)` truncation error and a variance that does
**not** grow as `h → 0`, because the two evaluations share `z` and the noise cancels in the
difference. That is exactly why a plateau exists.

*Count layer:*

    y_t(η; ω) ∈ ℤ_{≥0} .

For fixed `ω`, `η ↦ y_t(η; ω)` is integer-valued. An integer-valued function of a real variable
is piecewise constant: on any interval where it does not jump it is constant, so its derivative
is zero there. Hence

    ∂_η y_t(η; ω) = 0   for almost every η,   undefined on the (countable) jump set,

while `d/dη E[y_t] = λ_t′(η) ≠ 0`. **The pathwise derivative exists almost everywhere and is
zero almost everywhere, and it is the wrong number for every `ω`.** IPA is not noisy here; it
is *inconsistent*.

**This settles the brief's question.** The degeneracy follows from the output being
integer-valued and from nothing else. No sampler produces a non-integer count, so no choice of
random-number scheme removes it. **It is genuine, and it is a property of the observation
model, not of the code.**

**(b) Is `D_h` a good estimator of `d/dη E[s(y(η))]`?** This is the question the reported claim
actually needs, and it has a different answer.

`D_h` is not the pathwise derivative — it is a difference of two integers over `2h`. Take the
monotone inversion coupling `y_t(η) = F⁻¹_{λ_t(η)}(u_t)` with `u` frozen by the seed. Marginally
`y_t(η) ~ Poisson(λ_t(η))` for every `η`, so for the **linear** statistic `s = Σ_t y_t`,

    E[D_h]  =  [ Σ_t λ_t(η+h) − Σ_t λ_t(η−h) ] / (2h),

which is the central difference of the true mean **exactly, at every `h`**. So the estimator is
not biased toward zero. What diverges is the variance. Write `Δ = s(y(η+h)) − s(y(η−h))`; it is
an integer, and it is zero unless some coordinate's jump point falls inside `(η−h, η+h)`. The
jump set of coordinate `t` has local density proportional to `|λ_t′|`, so `P(Δ ≠ 0) = O(h)`
while `|Δ| ≥ 1` whenever it is non-zero. Therefore

    E[Δ²] = O(h)      and      Var[D_h] = E[Δ²]/(4h²) − (E[Δ]/2h)² = O(1/h),

and over `R` replicates `Var = O(1/(Rh)) → ∞` as `h → 0` at fixed `R`. There is no plateau,
because the noise term **diverges** rather than cancelling — the same `1/h` divergence the
no-CRN control exhibits, reached by a different route.

**What an analyst then sees.** At fixed `R`, `P(D_h = 0 for all R replicates) = (1 − O(h))^R`,
which tends to 1 as `h → 0`. So the prediction is that at small `h` almost every replicate
contributes exactly zero and the estimate is decided by the handful that do not.

**G3's "converges confidently to zero" is directionally right and is not what was measured.**
The measurement is in §3.3 and it is worth being precise about, because the two descriptions
suggest different things about how the failure would present itself. The failure is unbounded
variance in the `h → 0` limit, not systematic error. That distinction names the remedy: shrinking
`h` cannot help, and averaging at small `h` cannot help either — one would need `R ~ 1/h`. A bias
would have called for a different correction entirely. And the results files' phrasing *"either
exactly 0 or O(1/h)"* invites the bias reading, which is the one clause of the claim that should
be rewritten.

### 3.2 NumPy's sampler makes it worse, and is not the cause

`numpy.random.Generator.poisson` uses inversion only for `λ < 10` and transformed rejection
(PTRS) for `λ ≥ 10`, where the number of uniforms consumed depends on `λ` itself. With one
generator vectorised across `T` coordinates, a change in `λ` that flips a single acceptance
shifts the stream for **every later coordinate**, so one flip can change the whole remaining
series instead of one entry. Marginal unbiasedness survives — each `y_t` is still exactly
`Poisson(λ_t)` — so the estimator stays unbiased; what worsens is the variance and the
correlation structure of the jumps. The `poisson_inversion` coupling in the check is the
monotone alternative, included precisely so that "NumPy's sampler is bad" and "counts are bad"
can be told apart rather than assumed.

### 3.3 What was measured

`results/robustness/crn_count_check.yaml`, and §4 of the generated table. Three couplings applied
to the *same* deterministic mean, so the observation layer is the only thing that varies; test
statistic `final_size`, which is linear, so the target is exact.

**(i) The map is a step function under both count couplings, and under neither continuous one.**
Walking `η` through 801 points at one fixed seed: the lognormal layer gives **801 distinct
values and 0% of adjacent pairs exactly equal**; `poisson_numpy` gives **168 distinct values,
39.25% exactly equal**; `poisson_inversion` gives **168 distinct values, 48.50% exactly equal**.
**The monotone inversion coupling does not repair it.** That is the discriminator the check was
built around, and it answers the brief's question: **genuine degeneracy, not a sampler artefact.**

**(ii) The variance diverges as `1/h`, then as `1/√h`, exactly as derived.** The standard
deviation of a single replicate's difference quotient:

| coupling | `h = 10⁻¹` → `10⁻⁶` | ratio per 10× decrease in `h` |
|---|---|---|
| lognormal | `101.2` at every `h` | `1.00, 1.00, 1.00, 1.00, 1.00` |
| `poisson_numpy` | `150 → 3.46×10⁵` | `9.09, 8.80, 3.87, 3.16, 2.37` |
| `poisson_inversion` | `24.3 → 4.50×10⁴` | `7.31, 7.02, 3.52, 3.25, 3.16` |

**The lognormal row is the common-random-numbers property in one line: the variance does not
grow at all.** The count rows start near `10` per decade — the `1/h` regime, where a jump is
crossed almost every time — and cross over to near `√10 = 3.16`, the `1/√h` regime the
derivation predicts once `P(Δ ≠ 0) = O(h) ≪ 1`. **The crossover is visible in the data and it
was predicted before it was looked at.**

**(iii) Unbiasedness survives; usability does not.** At `R = 20,000` the relative bias is
`+0.0002` for the lognormal coupling at every `h`. For the count couplings it stays within
Monte Carlo error of zero throughout — the apparent drift at the smallest `h` is not
significant, because by then the standard error of the mean is itself comparable to the
quantity being estimated. So the estimator is **not** biased toward zero. What it is, is
useless: at `R = 128`, the replicate count the reported diagnostic uses, the fraction of
replicates returning **exactly zero** climbs `0.000 → 0.009 → 0.079 → 0.501 → 0.926 → 0.993`
for `poisson_numpy` across the sweep.

**(iv) What that looks like at the reported replicate count.** Against a true derivative of
`−866.6`, the `R = 128` estimates under `poisson_numpy` run
`−844.8, −1018, −359.4, 3125, 0, −3906`. At `h = 10⁻⁵` the estimate is **exactly zero**. At
`h = 10⁻⁶`, where 99.3% of replicates contribute nothing, both count couplings return
**`−3906.2`** — which is `−1 × 1/(2h) / 128`, i.e. the entire estimate is one replicate whose
count moved by one. The lognormal coupling returns `−859.4` at every `h` in the sweep.

**(v) The one correction to G3's wording.** The *sample standard deviation across replicates*
was **not** exactly zero at any `h` in this sweep, so the strongest form of "converges
confidently to zero" — a zero estimate with zero apparent spread — did not occur at `R = 128`.
What occurs is **worse in a different way**: the estimate is not stably zero, it is dominated by
rare single-count flips and swings between `0` and `3125` and `−3906` with no stability at all.
G3's *"either exactly 0 or O(1/h)"* is right about the two branches and its *"converges
confidently to zero"* describes only the first. The measured failure is unbounded variance, and
`audit/S3_REPORT.md` §4.1 and the `why_not_a_count_noise_model` field should say so.

### 3.4 Is it already known? Yes — it is the standing precondition of the whole literature

One targeted check on the corrected instrument (S4), as the brief specified, plus one
canonical-reference lookup. **The answer is unambiguous and it is not close.**

> **Pierre L'Ecuyer & Gaétan Perron**, *"On the Convergence Rates of IPA and FDC Derivative
> Estimators"*, **Operations Research 42(4): 643–656 (1994)**, DOI `10.1287/opre.42.4.643`.
> OpenAlex citation count **103**. FDC is *finite differences with common random numbers* — the
> estimator this project uses, named.
>
> > *"We show that **under the (sufficient) conditions usually given for infinitesimal
> > perturbation analysis (IPA) to apply** for derivative estimation, a finite-difference scheme
> > with common random numbers (FDC) has the same order of convergence, namely O(n^−1/2) …
> > **Our developments do not involve monotonicity, but are based on continuity and
> > smoothness.**"*

**The guarantee the CRN construction relies on is explicitly conditional on the sample path
being smooth.** Count output is the textbook case where that condition fails.

> **Shakir Mohamed, Mihaela Rosca, Michael Figurnov & Andriy Mnih**, *"Monte Carlo Gradient
> Estimation in Machine Learning"*, **JMLR 21: 1–63 (2020)**, arXiv:1906.10652, retrieved and
> read in full (30,892 words; control `the` = 2,109, `pathwise` 107, `score function` 80).
>
> > *"We will later find that **if the cost function is not differentiable, then the pathwise
> > gradient will not be applicable**."*
> > *"**If the measure is discrete on its domain then the score-function or measure-valued
> > gradient are available.**"*
> > *"Gong and Ho (1987) introduced **smoothed perturbation analysis** … to address cases where
> > the interchange of differentiation and integration is not applicable, such as when there are
> > **discontinuities in the cost function**."*

Full-text hit counts on the corrected instrument, control re-validated in the same batch
(`"expected number of draws required to obtain one acceptable"` → **1**, arXiv:2405.07026):
`"infinitesimal perturbation analysis" "sample path" discontinuous unbiased` → **29**;
`"smoothed perturbation analysis" discontinuous sample path` → **10**;
`"common random numbers" "finite difference" discrete-event derivative estimator discontinuous`
→ **9**; `"perturbation analysis" "discrete event" gradient estimator "does not" unbiased
Poisson` → **37**.

**Consequence.** G3's §4.1 presents this as a finding — *"This is a modelling constraint on any
simulation-based Jacobian, not an implementation detail"* — and the constraint is real. But it
is **not novel**, and the R2 framing decision (`docs/DECISIONS.md` D-6) applies to it with the
same force it applies to the rank screen: it is **cited infrastructure**. `docs/THRESHOLDS.md`
§1.4 now carries the L'Ecuyer & Perron citation next to the common-random-numbers paragraph,
which is where a reader needs it.

**The one thing that is not merely a restatement.** The *positive* half — that a continuous
multiplicative observation layer restores it, demonstrated against a count layer as a negative
control, on an epidemic simulator — is a legitimate modelling observation for the eventual
paper. It is a sentence in a methods section, not a contribution, and this project has learned
what happens when that distinction is blurred.

## 4. The argmax inside `S_A`'s peak statistics

**Verdict against G3's claim: the documented defence is WRONG for one of the two statistics it
claims to cover, and the reported numbers are nonetheless CLEAN. Both halves are measured below
rather than argued.**

`audit/S3_REPORT.md` §4.2 reports that argmax-defined summaries are not finite-differentiable
and that both peak statistics are therefore computed by parabolic interpolation. The brief asks
whether this *"silently contaminates the S_A results already reported"*, since peak time is one
of `S_A`'s four coordinates.

The check found the concern was aimed at the wrong statistic. **The interpolation does rescue
peak time. It does not rescue peak height, and `src/simulators/summaries.py` claimed it did.**

### 4.1 The defence, and where it fails

The docstring asserted that the interpolated location and height *"remain continuous across a
change of the discrete argmax (at the switch point the peak sits midway between two bins and
both parabolas agree there)."*

Take the adjacent-bin case the parenthesis describes: at the switch the two bins are tied. Write
`a = y[i−1]`, `m = y[i] = y[i+1]`, `c = y[i+2]`. The parabola through `(i−1, i, i+1)` has vertex
offset `+½` and height `m + (m−a)/8`; the parabola through `(i, i+1, i+2)` has vertex offset
`−½` from index `i+1` and height `m + (m−c)/8`.

    location:   i + ½   from the left,   (i+1) − ½ = i + ½   from the right.   EQUAL.
    height:     m + (m−a)/8             m + (m−c)/8                            EQUAL ONLY IF a = c.

**The location claim is true. The height claim is false, and the jump is `(a−c)/8`** — an
eighth of the gap between the two outer neighbours. This is asserted as a test in
`tests/test_summaries.py` and the docstring is corrected.

**Why it survived.** The test that existed,
`test_peak_interpolation_is_continuous_where_the_discrete_argmax_moves`, swept a **symmetric**
parabola, for which `a = c` and the height jump is identically zero by construction, and it
discarded the height it computed (`loc, _h = peak_interpolated(...)`). Its docstring stated the
general claim; its body could only ever exercise the single case in which that claim holds. See
finding 5.

### 4.2 There is a second kind of switch, and the algebra above does not cover it

The adjacent-bin analysis assumes the argmax moves from `i` to `i+1` through a tie between
neighbouring bins. With a lognormal observation layer at `obs_sigma = 0.15`, the reported curve
is noisy across a broad, flat epidemic peak, and the global argmax can instead jump between two
**separated** local maxima when their heights cross. There is no tie between adjacent bins
there, no midpoint, and no reason for either statistic to be continuous: **peak time jumps by
the index gap, and peak height jumps as well.** This is the more damaging case and the
interpolation does nothing about it.

### 4.3 Whether it actually contaminated the reported numbers

Three measurements, in `results/robustness/summary_smoothness_check.yaml` and §3 of the
generated table.

**(i) A fine `η` walk at one fixed seed**, which locates real switches and measures the jump in
each statistic across them.

**(ii) A census at the estimator's own settings.** For each component, at the largest step size
in the pre-registered sweep and at the representative one, how many of the `R = 128` replicates
actually had `argmax(y(+h)) ≠ argmax(y(−h))`? A discontinuity that is never straddled cannot
contaminate anything; one straddled by a large fraction of replicates is not a caveat but the
result.

**(iii) Leave-one-coordinate-out.** `S_A`'s verdict recomputed with each of its four coordinates
dropped in turn, and with both peak statistics dropped together. If the verdict survives without
them, it does not rest on them — a stronger statement than any argument about how well the
interpolation behaves.

**The measured answer: the reported numbers are clean, and they are clean for a reason worth
knowing rather than by luck.**

**(i) Real switches exist and both statistics jump at them.** Walking `η` at one fixed seed:
the transmission family produces **1** argmax switch and the progression family **2** over the
swept range; the observation family produces **0**, which is the expected sanity check — a pure
reporting-fraction multiplier rescales the whole series and cannot move its argmax. At those
switches the largest single-step change in peak time is **3.169 days** (progression), against a
median step of a small fraction of a day: that is the **separated-maxima** case of §4.2, not the
adjacent-bin case, and it moves peak time as well as peak height. Peak height's largest step is
**170.2** (transmission).

**(ii) At the step size the reported verdict is read from, no replicate crossed one.** The
census, at `R = 128` replicates for each of the three components:

| `h` | transmission | progression | observation |
|---|---|---|---|
| `10⁻¹` (largest in the sweep) | 1 / 128 | 5 / 128 | 0 / 128 |
| `10⁻⁴` (the representative `h`) | **0 / 128** | **0 / 128** | **0 / 128** |

**The reported `S_A` Jacobian is read at `h = 10⁻⁴`, and nothing straddled a discontinuity
there.** That is not a lucky draw: the probability of straddling scales as `O(h)`, so scaling
the `h = 10⁻¹` rate down by a thousand predicts about `0.015` straddling replicate–component
pairs at `h = 10⁻⁴`. **Observing zero is what the theory predicts.** The small-`h` end of the
plateau protects the estimate here, and it is worth noting that it protects it *for a reason the
project did not know it needed* — the plateau rule was fixed to control truncation and noise,
not discontinuity crossings.

**(iii) But the coordinate carrying the discontinuity is the one the verdict rests on.**
Recomputing `S_A`'s verdict with each coordinate dropped in turn, at the representative `h`:

| `S_A` computed with | `κ` | rank at `τ` | verdict |
|---|---|---|---|
| all four coordinates | **5.378** | 3 | separable |
| dropping **peak time** | **5.379** | 3 | separable |
| dropping **peak height** | **1165** | 2 | INSEPARABLE |
| dropping final size | 753.4 | 2 | INSEPARABLE |
| dropping growth rate | 265.3 | 2 | INSEPARABLE |
| dropping **both peak statistics** | `inf` | 2 | INSEPARABLE |

Read the first two rows together. **Peak time — the coordinate whose non-differentiability G3
raised — contributes nothing: removing it moves `κ` from 5.378 to 5.379.** Peak height — the
coordinate whose discontinuity G3 did not notice, and whose continuity the docstring positively
asserted — is load-bearing: without it `S_A` is inseparable at `κ = 1165`.

**So the concern was aimed at the inert coordinate and the real defect sits in a coordinate the
verdict depends on.** The numbers survive; the reasoning that was supposed to protect them did
not.

*(One caveat on reading that table, since it would be easy to over-read: dropping any coordinate
leaves `d = 3 = K`, a square system, which raises `κ` for reasons having nothing to do with
which coordinate went. The informative comparison is the **relative** one — every removal except
peak time's raises `κ` by a factor between 49 and 217, and peak time's raises it by 1.0002.)*

### 4.4 What was changed, and what was not

- `src/simulators/summaries.py`'s docstring is **corrected**: it now states which half of the
  claim is true, gives the `(a−c)/8` jump, and names the separated-maxima case it never covered.
- `tests/test_summaries.py` is **split**: the location claim is pinned on an *asymmetric* curve
  (so it is a test rather than a tautology), the height discontinuity is asserted with its exact
  size, and the special case `a = c` in which the original docstring was right is kept and
  labelled as the special case.
- **No summary was redefined and nothing was recomputed.** Changing the peak estimator after
  seeing the results is precisely the move `LEDGER_DESIGN.md` D3 forbids, and it is not needed:
  the measurement says the reported numbers are unaffected.

## 5. Three defects found by applying the project's own rule to the project's own output

The brief's standing constraint **S3** generalises `DEVIATIONS.md` D-8: *"Before writing ANY
provenance or validity flag this session, ask explicitly: under what condition would this flag
read FALSE? If you cannot construct a realistic case where it does, the flag is vacuous and
must not be written as if it were a check."* Applied to what G3 wrote rather than to what this
session writes, it finds three things. None of them changes a singular value. All three are in
the machinery that is supposed to make the singular values trustworthy, which is why they are
reported rather than fixed quietly.

### 5.1 `leakage_checked: true` was a literal

Every file in `results/` carries `leakage_checked: true` next to a paragraph explaining why
there is no ground truth available to leak. **Nothing computed the boolean.** In
`src/diagnostics/run_diagnostic.py` it was written as the Python literal `True`, in two places.
There is no condition under which it could have read `false` — not a subtle one, not an
unlikely one, none.

The prose statement it accompanied is sound: the diagnostic receives the simulator as a
callable, the distortion basis, and the resulting summary vectors, and computes a property of
the map `s(η)` rather than a guess about a hidden truth. **The argument is fine. The field
claiming the argument had been checked was not a check**, and `leakage_checked` is a stronger
word than `leakage_argued`.

**The fix, and why it is a fix rather than a rename.** The testable content of the claim is
**equivariance under relabelling the components**. If the diagnostic holds no privileged
knowledge about which column is which, permuting the columns must leave the singular values,
the numerical rank and the condition number unchanged, and must permute the column norms, the
coherence matrix and the near-null right singular vectors (up to the sign the SVD does not fix)
correspondingly. Any component-indexed special case breaks it. `jacobian_rank.leakage_check`
runs all `K! − 1` non-identity permutations and reports the worst discrepancy in each quantity.

Under what condition does *that* read false? A threshold applied to one named column; an
assumption that column 2 is the observation component; an ordering dependence in the
equivalence-class rule. `tests/test_jacobian_rank.py` injects exactly such an analysis and
requires the check to catch it, so the check has been seen giving the opposite answer — which
is D-8's own stated remedy and the thing the literal could never be subjected to.

**What it does not establish, stated because the previous field's problem was overclaiming.**
Equivariance is necessary, not sufficient. A leak that treated all three components
symmetrically would pass it. The prose argument remains the substance; this is the part of it
that is mechanically checkable.

**The existing results files were not regenerated.** Re-running the diagnostic to change a
metadata field would overwrite the numbers session G3 recorded, which is exactly what a session
auditing those numbers must not do. Every file in `results/` therefore still carries the
literal, and this paragraph is the notice that it is one.

### 5.2 The test guarding the peak-interpolation claim could not fail

Covered in finding 4. Recorded here as well because it is the same class:
`test_peak_interpolation_is_continuous_where_the_discrete_argmax_moves` swept a **symmetric**
parabola, for which the two outer neighbours are equal and the height discontinuity is
identically zero by construction, and it discarded the height it computed. Its docstring
asserted the general claim; its body could only ever have exercised the one case in which the
claim is true, on the one statistic for which it is true.

### 5.3 `dirty_paths` — the field D-8 added to make `dirty` informative was corrupting a path

Found by reading this session's own first results file, which recorded
`dirty_paths: [rc/simulators/sir3.py]` for a modification to `src/simulators/sir3.py`.
`src/provenance.py` read `git status --porcelain -uno` through a helper that strips the output;
the porcelain format is column-sensitive and an unstaged modification puts a space in the first
column, so stripping ate the first line's leading space and the caller's `line[3:]` then lost
one character of that one path.

**Why it is worth naming rather than fixing silently.** D-8 records that the `dirty` boolean
was structurally guaranteed true and therefore uninformative, and that the remedy was to add
`dirty_paths` so a reader could see *which* files were dirty rather than only *that* some were.
**The field added to repair D-8 was itself wrong from the day it was written**, and its failure
mode is D-8's own: a reader who checked would find no file at that path and would learn to
distrust the field. It survived because it corrupts only the first line, only when that line is
an unstaged modification, and only by one character — so every clean run recorded
`dirty_paths: []` and showed nothing. There was no test. Full account in `DEVIATIONS.md`
**D-10**; `tests/test_provenance.py` is new and pins four properties the module had none for.

**No G3 results file is affected.** All five were written from a clean tree and record
`dirty_paths: []`.
